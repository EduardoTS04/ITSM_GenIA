# Database migrations

Alembic owns the database schema. The app no longer creates or alters tables on
boot, so **`alembic upgrade head` is a required setup and deploy step**.

Run every command from the `backend/` directory. The database URL comes from
`DATABASE_URL` through `app/core/config.py`, the same source the app uses, so
there is no separate URL to keep in sync in `alembic.ini`.

## Setup and deploy

```bash
pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

The Docker images already run `alembic upgrade head` before starting uvicorn, so
`docker compose up` needs no extra step.

## Everyday commands

| Task | Command |
| --- | --- |
| Apply all pending migrations | `alembic upgrade head` |
| Show the revision a database is on | `alembic current` |
| List the revision history | `alembic history --verbose` |
| Create a migration from model changes | `alembic revision --autogenerate -m "what changed"` |
| Roll back one revision | `alembic downgrade -1` |
| Preview the SQL without running it | `alembic upgrade head --sql` |

Always read an autogenerated migration before committing it. SQLite cannot alter
most columns in place, so `env.py` enables Alembic's batch mode
(`render_as_batch=True`), which rewrites the table instead.

## Revisions

| Revision | Contents |
| --- | --- |
| `0001` | Baseline: `tickets` and `comments`, including the five ticket columns the old `run_migrations()` helper added by hand |
| `0002` | `agent_traces`, the agent execution trace from the pipeline observability work |

## Adopting Alembic on an existing database

An existing `data/itsm.db` must not be re-created. Check which tables it already
has, then stamp it at the matching revision so Alembic knows where it stands:

```bash
python -c "import sqlite3,sys; print(sorted(r[0] for r in sqlite3.connect(sys.argv[1]).execute(\"select name from sqlite_master where type='table'\")))" data/itsm.db
```

| What the database contains | What to run |
| --- | --- |
| `tickets` + `comments` + `agent_traces` | `alembic stamp head` |
| `tickets` + `comments` only | `alembic stamp 0001` then `alembic upgrade head` |
| Nothing (new or empty file) | `alembic upgrade head` |

`alembic stamp` only writes the `alembic_version` table; it never touches your
rows. Both revisions match the schema those databases already have, column for
column, which is what makes stamping safe.

## The dev-only escape hatch

`AUTO_CREATE_SCHEMA=true` makes the app build missing tables from the ORM models
at startup, as it used to. It defaults to `false` and is meant only for
throwaway databases — it bypasses Alembic and leaves the database unstamped.
